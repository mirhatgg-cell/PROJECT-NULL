# V10 — серверные системы

`ProjectNullServer_V10.server.luau` исполняется в `ServerScriptService/ProjectNullV10`. Рядом находятся модули `ExperimentCore` и `Content`; общие RemoteEvent `Request` и `Push` — в `ReplicatedStorage/ProjectNullV10`. Источник правил — серверный модуль экспериментов. Клиент получает снимок состояния и отправляет действия, но не задаёт результат, урон, температуру или найденные документы.

## Физический доступ

Для взаимодействия деталь содержит `V10_Interact/Action`, `V10_Interact/Argument` и `V10_Prompt`. Сервер проверяет живого персонажа, действительное положение детали внутри комплекса, дальность и прямое попадание серверного луча именно в цель. Цель доступна для запросов (`CanQuery=true`). Невидимость цели, стена, выключенная подсказка и подмена аргумента не дают доступ.

Терминал закреплён за одним протоколом. Калибровка, запуск и ответы требуют сохранённого доступа к его физической детали, близости и видимости. Закрытие экранной панели сохраняет этот якорь: участник может отвечать через компактную панель, пока остаётся у пульта. Удалённый аварийный останов допускается для живого владельца активного опыта. Другой игрок не может отвечать, сбрасывать или останавливать занятый протокол. Уход от неактивного пульта (`idle`, `completed`, `failed`) освобождает резервирование через 15 секунд без новой ошибки и ущерба. Уже записанный результат остаётся в личном журнале. Подготовленный или запущенный опыт автоматически этим правилом не сбрасывается.

В P-02 экранный ответ запрещён: владелец активной серии должен подойти к одному из трёх реальных датчиков и удержать E. В P-04 сервер наблюдает горизонтальное смещение `HumanoidRootPart`. Флаг движения клиента не принимается: ответ «пройти» без действительного шага не работает, а движение при открытой оптике прерывает серию. Возле пульта достаточно сделать небольшой шаг; ходить через занятые стойки не требуется.

Для P-03 перед калибровкой необходимо самостоятельно открыть официальную сводку `DOC_P03_LOG` в E-04 и подписанный журнал `DOC_P03_CORRECTION` в E-07. Оба документа добавляются в личный журнал. Список недостающих свидетельств с названиями помещений виден на пульте; выбирать протокол можно заранее.

Все запросы проходят ограничение частоты. Ремонт, охлаждение, помощь и получение расходников разрешены у соответствующих постов. Выдача расходников имеет общий интервал 45 секунд, помощь — 20 секунд на участника. Ремонт и помощь подчиняются фазе и запасам из модуля экспериментов.

## Реальные связи и последствия

Перед действием и на каждом серверном шаге читаются существующие `Controls/Circuits/Computers`, `Ventilation`, `AcousticAmplifiers`, `PhysicalHall`. Поэтому прежние автоматы и аварийная кнопка V9 действительно влияют на новые серии. Прежний контроллер F-02 остаётся самостоятельным приборным упражнением; сервер V10 не переопределяет его приводы и основные двери.

Ошибки модуля вызывают ограниченный урон живому владельцу один раз за событие. Медицинское событие восстанавливает не более 25 здоровья с ограничением `MaxHealth`. Смерть или выход владельца прерывают испытание; при выходе пульт освобождается после записи причины. Сотрудники TECH/MEDIC отвечают с учётом текущей фазы и числа принятых личных протоколов.

Физические выходы обновляются при действии и с интервалом 0,1 секунды: три световых канала P-01, измерения/вводящие в заблуждение вывески трёх датчиков P-02, шторка оптики P-04, независимый измерительный канал P-05. Шторка закрывает оптику при `occluded` и в ожидании; при открытом наблюдении сдвигается на свой `OpenOffset`. Общие маяки и статусы отражают ожидание, испытание и остановку. В основных геометрических частях коллизии не отключаются.

## Журнал и сохранение

DataStore `PROJECT_NULL_PROGRESS_V10`, ключ `u_<UserId>`, сохраняет найденные документы, принятые протоколы, число попыток по протоколам и последние 20 результатов. У записей постоянные ID; повторное сохранение объединяет их без дублирования. Сохранения разных сессий объединяют открытые документы и завершённые протоколы через `UpdateAsync`.

Загрузка выполняется асинхронно. Документ, найденный во время загрузки, сохраняется после объединения с прежними данными. Если чтение не удалось, сервер запрещает запись поверх неизвестного профиля и повторяет загрузку позже. Выход во время загрузки также учитывается. Есть ручное сохранение, автозапись раз в 60 секунд, запись при выходе и ограниченное ожидание при завершении сервера.

В неопубликованном месте (`GameId=0`) и для локальных тестовых участников Studio с неположительным `UserId` используется только память текущей сессии. Отрицательные ID Studio допустимы для серверного владения протоколом, но не используются для чтения или записи постоянного профиля. Если DataStore/API недоступны, интерфейс сообщает об этом и не показывает ложное «сохранено». Для проверки постоянного прогресса необходимо опубликовать тестовое место и проверить доступ к API в Studio либо войти в опубликованную игру. Настройки публикации и доступ к API этот файл не меняет.

В снимок клиента попадают полные тексты только лично найденных документов. Личный профиль другого игрока не отправляется. Журнал можно перечитывать без возвращения к каждой бумаге; действия с оборудованием по-прежнему требуют физического доступа.

## Проверка

`tools/test_v10_server_runtime.py` исполняет настоящий текст этого скрипта и настоящий модуль экспериментов в Lua VM с управляемыми заменами API Roblox. Проверяются доступ, видимость, владение, ресурсы, ложные удалённые запросы, обнаружение документов, реальные движения для P-04, физический ответ P-02, последствия и обработка сохранений.

Это проверка логики. Реальные персонажи, отображение, сетевые задержки, звук, коллизии и DataStore в Roblox Studio требуют отдельного прохода. Наличие автоматических тестов не означает прохождение проверки в движке.
